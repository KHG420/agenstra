# Sub2API 第二轮真实任务评测

2026-10-03，在框架与 Sub2API 的独立工作树、专用本地服务及合成数据库中，继续通过宿主身份换票、同源代理和正式无 UI SDK 执行真实模型任务。基线是 `fc1c229`，模型为 `deepseek-v4-flash`，决策开启 thinking、推理强度 low，记忆提取关闭 thinking；预算为 20 个模型轮、40 次工具调用及 180 秒。这里的请求次数包含记忆提取、格式恢复和完成复核。

## 第一批结果与定位

| 场景 | 结果 | 模型请求 | 核对内容 |
| --- | --- | --- | --- |
| 会员读取自己资料 | 通过 | 4 | 身份、邮箱、余额与并发；业务 handler 仅访问自己的资料。 |
| 创建分组 → 修改刚创建的分组 → 读回 | 通过，3 条消息 | 21 | 实际创建 ID、一次创建及一次修改、平台、倍率、状态与后端值。 |
| 缺少创建参数后追问 | 失败 | 3 | 两次决策格式错误，未调用业务 handler。 |
| 修改分组时在审批处刷新 | 通过 | 10 | 保留会话、generation 只增加一次；写入 handler 仅执行一次。 |
| 审批前改口并丢失 steering 响应 | 通过 | 10 | 相同 request ID 重试；仅一条改口事件、零写入，业务值不变。 |

第一批共 7 次运行、48 个模型请求。之后单独重跑缺参数场景，再次失败，3 个模型请求。诊断的 `model_decision_schema_invalid` 不能说明具体错误，因此在本地增加临时诊断代理，仅将请求正文与响应保存到被忽略的私有目录，未保存或提交认证头。

实际模型连续两次返回 `input_schema: {"type":"string","enum":[…]}`。这是普通 JSON Schema 的合法组合，但框架的 `RequestedInputSchema` 是单字段文本输入契约：枚举要求 `type:"enum"`，`type:"string"` 禁止枚举。原有运行时提示只写了 string、enum、date 三个类型，没有提供其准确 JSON 形状；通用格式重试未补足信息，模型再次返回同一错误。

## 框架修复与验证

运行时现在明确给出 string、date、enum 的 JSON 形状，说明这是单个文本答案的契约，并给出可解析的枚举示例；组合答案可以省略 `input_schema`。修改位于运行时的决策补充提示，保留能力包提示及其持久指纹，未改变 HTTP、SDK 或持久化结构，也未放宽校验。

回归测试先返回实际观察到的 string+enum 错误响应，再从框架发给模型的提示中读取枚举示例，走正式 HTTP 模型适配器与 Runtime 格式恢复路径。测试在修复前失败，修复后进入 `needs_input`，同时保留非法答案拒绝和模型用量记录。上下文测试按当前运行时固定提示预留空间，仍检查实际总输入上限、历史裁剪、完整 Fact 引用及超限时不调用模型；记忆超限测试独立构造大提取源与可容纳的业务请求，避免依赖两段固定提示的长度差。

真实模型复测：较长的中间提示完成了两次追问及创建，10 个模型请求；最终压缩提示完成了组合追问及创建，8 个模型请求，实际后端平台为 gemini、倍率为 1.25。两个试验都保留了审批参数和成功回执。小样本说明已能完成触发任务，不能据此声称模型永远不会再产生非法决策，也不能把失败时的 3 次请求与完成任务的 8 次请求当作性能对比。

同一批中另一个刷新用例因测试脚本复用了刚创建的分组名而失败：后端拒绝重复创建，模型正确报告拒绝，最终断言找不到新创建对象。该结果归类为测试夹具问题，未计入框架修复成功；后续用例改用独立名称。

`make check` 通过：格式与空白检查、Go/JS 静态检查、Go 竞态测试、97 项 Web 测试以及命令构建。脱敏证据见 [第二轮证据](evidence/sub2api-stress-round2-2026-10-03.json)。证据保留失败及中间方案，私有模型请求正文、凭据及数据库未提交。

## 推送后的密集使用

输入契约修复以 `76ca878` 推送 main 后，继续执行 25 个业务场景，包含密集分页、实体混查、8 条消息的连续会话、排队修改、排队取消、恢复响应丢失后重新加载、连续三次回执 ACK 响应丢失、拒绝与取消审批、会员权限、创建后修改与读回、输入期间刷新、非法单选答案、提交前及实际写入后的改口，以及三轮各三个并发修改与后续读回。

25/25 场景通过，共 48 条消息：47 次运行已发布，其中 46 completed、1 按要求 cancelled；另 1 条消息在排队时取消，未发布运行。运行账本计入 323 个模型请求（322 个有 usage，1 个在取消边界使用估算），实际调用 110 次业务 handler，其中 18 次写操作。全部八个已接入业务能力都实际调用：my_profile、list/get/update_user、list/get/create/update_group。测试检查真实业务值、审批参数、回执和事件数量，而非只检查 completed。

仍出现被格式恢复机制纠正的模型决策错误；审批拒绝、取消和被改口废弃的调用也保留在诊断中。25/25 是场景断言的结果，不表示每次模型输出都合法。完整逐次用量、回执与诊断见 [密集使用证据](evidence/sub2api-stress-round2-intensive-2026-10-03.json)。

## 临时任务误记与遗忘投影

密集使用中发现，模型把“取消刚才的修改要求。不要修改任何用户，只重新读取 Page5 的当前资料，用表格回答”提取成 `explicit` 项目约束，之后无关分组查询也提到了这项规则。Host 的引文校验能保证原文确实出现过，但不能证明原文包含长期意图。

用相同模型、deepseek_chat API、thinking disabled 对六种合成输入各测试两次：基线 11/12 正确，其中一次把改口归为长期约束；明确任务级指令的作用范围后 12/12 正确，明确要求“以后”的规则与语言偏好仍保留。提取提示现在明确取消、改口、只读、审批选择和缺参数追问通常作用于当前任务，旧记忆不能替当前原文提供长期意图。此次配对测试各 12 次请求，input tokens 为 5836 / 6688，output tokens 为 525 / 326；这是语义分类样本，不能据此保证任意模型的准确率或宣称性能提升。普通 CI 不调用模型；显式评测入口为 `TestLiveMemoryTaskScopeEvaluation`，见 [记忆评测证据](evidence/sub2api-memory-scope-2026-10-03.json)。

只改提示的完整宿主复测仍为 4/5：隔离库通过正式 SDK 遗忘的旧记录，又被提取模型重建。继续追踪发现 `prepareMemories` 将 `listMemories` 返回的 forgotten 条目投影为无状态的 MemoryView，并在过滤之前取 32 条。即使其值和引文已经清空，主题名称仍可能引导模型把当前业务命令归为旧长期规则；已遗忘条目还会占满投影位置。

框架现在先排除 forgotten，再选至多 32 个提取辅助条目，保留有效默认值和正在形成的习惯候选。新增 SQLite/模型替身回归测试在修复前失败，修复后即使有 33 条遗忘记录也不会发送它们，并仍能发送较早的有效语言偏好和表格习惯候选。遗忘、来源去重与重新学习的持久规则沿用原路径。

完整修复后的同一组宿主复测 5/5：缺参数追问、输入处刷新并拒绝非法选择、已写入后的改口、临时改口后查询无关实体且不建立长期约束，以及明确“以后用中文”的偏好跨消息生效。共 7 条消息、54 个模型请求、16 次业务 handler；临时改口提取的 Existing 从中间方案的 15 条降到 1 条合法候选。隔离库两次通过 SDK 遗忘历史合成记忆，保留重置前证据；框架修复不批量重写真实宿主历史数据。两种宿主试验的失败、成功、实际候选及提取输入见 [遗忘投影证据](evidence/sub2api-memory-projection-2026-10-03.json)。

最终 `make check` 再次通过。两项修复均不需要宿主增加 Agent 编排、记忆过滤或输入格式补丁；公共 API、SDK、传输格式、数据库结构及生产依赖均沿用现有契约。

## 本轮总账

本轮从第一批发现、定位复现、中间方案、推送后密集使用到最终宿主复测，共 44 次场景执行、73 条消息。72 次运行已发布：69 completed、2 次输入契约复现 failed、1 按要求 cancelled；另 1 条排队消息取消且未发布。场景断言 40/44 通过，四次失败分别是两次输入契约复现、一次测试夹具重名、一次只修改记忆提示仍未解决遗忘投影问题。未将中间失败抹掉。

完整运行账本计入 504 个模型请求，另有 24 次独立的记忆模型评测，总计 528 个计账请求。业务 handler 与写入次数、usage/估算区别及全部运行 ID 见 [本轮总账](evidence/sub2api-round2-summary-2026-10-03.json)。真实模型、审批和读回耗时会随模型服务与任务变化；这些结果仅覆盖本轮明确列出的八个能力与合成场景。
