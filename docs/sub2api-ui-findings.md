## 定位并修正的问题

**路由组件卸载的接入指导没有区分本地停止与永久关闭。** 原宿主的 `onBeforeUnmount` 调用默认 `client.destroy()`；该方法按既有契约关闭服务端浏览器 session。返回页面时新 client 建立新 session，原任务仍绑定已关闭的旧 session。实际创建任务连续五次读取上下文返回 `browser_offline`，页面却显示新连接正常，最终没有创建分组。

SDK 已提供 `destroy({ closeSession: false })`，不需要改变公共接口或默认语义。框架的快速接入、Web 接入与类型注释现在明确：优先让应用或登录会话持有 client，路由只挂载和卸载视图；路由自有 client 卸载时保留绑定，永久关闭用于退出登录或明确结束绑定。保留存储后重建 client 才能自动恢复；离开期间没有 client 处理任务时，原期限仍然生效。宿主实验工作树将卸载改为保留会话，并通过同一路由往返、补充信息、审批、真实创建复测。

**正常取消被聊天组件显示成请求失败。** Host 对主动停止保存 `status: cancelled`、`error_code: cancel_requested`。组件此前对所有 message.error_code 都展示通用错误，所以页面同时出现“已停止”和“请求未完成，请检查连接或重试”。根因是状态渲染，未发生取消请求失败。

组件现在仅在已取消且错误码为 `cancel_requested` 时省略通用错误，继续显示停止状态。其他错误、已成功回执及结果不确定的写回执沿用原展示路径。新增中英文回归在旧代码上失败，修复后通过，覆盖正常停止、停止后的不确定写回执及其他真实错误。导出更新 SDK 后，真实刷新历史和新发起的停止任务均不再出现误报。

## 保留的现象与验收边界

审批期间刷新会使旧页面上下文失效。一次审批后的调用先返回 `browser_context_required`，业务 handler 未执行；模型重新读取上下文并请求第二次审批后才完成。这是当前版本保护的真实表现，本轮没有绕过版本检查，也没有声称恢复后不需要再次审批。

路由问题的修复前任务在运行层最终为 completed，但回答明确“无法创建”，实际没有写入。因此本轮保存一例业务验收失败，不能用 12 completed 宣称 12 次业务目标全部完成；修复后新创建任务及后续修改均有真实成功回执。普通用户的权限拒绝与用户主动取消按控制流程验收，也不计为业务修改成功。

本轮仅验收桌面 Chrome，没有做移动端、其他浏览器或网络故障注入。运行中直接改口的 SDK 方法仍由此前专项测试覆盖，本轮界面只测试停止旧任务后发送替代要求。真实模型样本不能保证所有自然语言任务均可靠完成。
