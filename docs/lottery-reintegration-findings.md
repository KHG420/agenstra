# 年会抽奖从零重新接入验收（2026-10-03）

本次从 main 的 `eb71cc0` 创建框架 `codex/lottery-reintegration` 工作树；抽奖宿主从 `5210c90` 创建 `codex/agent-reintegration` 工作树，将用户当前未提交的原业务源代码保留为 `15e8891` 接入前快照，再实现新的接入并提交为 `1ad3db9`。两个原始目录均未编辑。没有复用上一次抽奖接入的 handlers。

验收使用单独的本机 D1/SQLite 数据目录及 156 位虚构样例员工，未使用真实活动名单。真实模型请求为 `deepseek-v4-flash`；透明测试网关只记录模型、thinking、推理强度、耗时和 HTTP 状态，不记录提示词、响应正文或密钥。完整脱敏指标见 [evidence/lottery-reintegration-2026-10-03.json](evidence/lottery-reintegration-2026-10-03.json)。

## 宿主实际需要做的工作

1. 用一个 frontend profile 声明页面观察和 10 个动作：查询活动/中奖者，开始/揭晓/取消，选择奖项，切换主题，打开/关闭面板，翻页。开始、揭晓和取消需要框架审批。
2. 将 typed handlers 绑定到原活动读取、命令提交和舞台函数；保留原服务的随机抽取、数据库保存、业务 revision 和丢失响应后的核对逻辑。只对已证明没有副作用的失败抛 `AgenstraActionError`。
3. 使用已有登录身份在服务端换短期票据，提供同源 `/agent` 代理，保留三个必要校验头。长期 key 仅在 Worker bindings 中。
4. 父组件持有 SDK；聊天视图借用 SDK，在切换后台/中奖名单面板时只卸载视图。宿主不编写模型循环、Agent 上下文、审批队列或回执恢复机制。
5. 配置框架 business/memory 模型 profile、授权、数据库和运行预算，导出零运行依赖的 SDK 并构建。宿主工作树的 `agent/README.md` 提供本机启动步骤。

页面观察包含奖项、阶段、轮次、计数和 revision，未包含完整人员名单；按需读取中奖者时才返回业务保存的人员快照。

## 已修复的框架缺陷

| 问题 | 复现和根因 | 修复与验证 |
| --- | --- | --- |
| 正常审批等待造成页面事实过期 | `ui.get_context` 的引用按读取时 `LastSeen + 30` 到期，之后在线心跳不会更新该 Fact。两次揭晓在批准后报 `fact_reference_expired`，引发重读和再次审批。 | 页面上下文改为带 revision 的持久快照引用；动作投递/开始时仍检查在线、代次、权限及页面 revision。回归验证等待 45 秒后未变页面可执行、编辑页面拒绝、离线不投递；真实模型等待 59.543 秒后一次揭晓成功。其他 Fact 到期、审批期限和总时限保留。 |
| 浏览器桥接失败仍显示“已连接” | 宿主漏转发页面会话 key，观察返回 401；成功的聊天历史轮询覆盖桥接失败状态。 | 记录桥接是否成功，浏览器模式的聊天轮询只能在桥接可用时报告已连接。初次失败及短暂断连恢复均有回归测试。 |
| 页面 key 的 401 重复交换登录票据 | SDK 遇到任意 401 都换票重发，但登录票据无法修复 `browser_session_invalid`。 | 仅 `unauthorized` 换票一次；页面会话错误直接保留。测试确认页面 key 失败只发一次请求，正常票据过期仍会刷新。 |
| 空对象动作类型错误、导出产物造成宿主 lint 失败 | 无参数动作生成 `{}`，TypeScript 也接受数字/字符串。模板生成未使用参数；现有事件回调的 permissive `any` 被宿主 lint 拒绝。 | 闭合空对象生成 `Record<string, never>`，patternProperties 仍允许其动态键；模板移除未使用参数；仅为兼容的异构事件回调标注精确 lint 例外，保留公共 API。宿主编译验证数字、字符串和额外键被拒绝，lint 通过。 |
| 同源代理接线说明不完整 | 文档只说明去掉 `/agent` 前缀，未列出 `X-Agenstra-Browser-Key`；接入时漏转发导致浏览器操作全部 401。 | 在 web-integration 文档中列出三个必需头及短期票据/页面会话的排错区别。宿主补齐转发后真实发送、恢复及动作回执成功。 |

本机入口最初也拒绝自动化跨站导航，属于原宿主来源检查。独立测试启动器加了一个只提供同源链接、不含业务数据的静态入口；原本机启动器的来源检查未变。

## 模型调用证据及边界

本次正常只读、开始、修复后揭晓分别为 **4 / 5 / 6 次请求**，其中每个任务有 1 次 memory extraction，业务决策分别 3 / 4 / 5 次。组合的主题切换及拒绝下一轮审批用了 7 次。7 个尝试总计 42 次，7 次 memory 使用 thinking disabled，35 次 business 使用 thinking enabled、reasoning_effort low；网关实际收到的参数与框架记录一致，42 个上游 HTTP 响应均为 200。

修复前两个揭晓尝试分别用了 7 和 9 次请求，最终分别因总时限和模型输出截断失败，未落库。它们包含重复审批后的额外决策；修复后等待超过 30 秒仍能成功，不再因该快照的固定心跳到期重复审批。但提示词、审批等待及执行环境不同，这不是与上一轮 10/6/26/6 的受控性能对比，不据此计算降幅。模型仍可能选择额外读取、输出不精确文字或触达输出预算，不能将当前样例等同于全面可靠性或成本证明。

没有价格配置，遥测 `cost_available=false`；报告里的 `estimated_cost_usd=0` 表示不可计算，不能解释为免费。本次仅验收本机、单管理员、桌面和虚构样例；未验收云端部署、多用户或生产活动。

## 围绕接入目标的后续框架优化

继续检查接入中暴露出的模型负担与恢复路径，复现并修复了以下三项问题。宿主 handlers、业务数据和模型默认参数没有调整。

| 问题 | 修复与验证 |
| --- | --- |
| 同一动作和框架轮询重复占用模型观察，并放大完成计数 | 原动作已经指向同一 invocation 的当前 Fact 时，省略重复轮询视图。6 个动作的回归由 12 条观察/12 次完成改为 6 条/6 次，完整审计记录不变；独立轮询、其他 invocation、失败和 unknown 仍保留对应证据。 |
| 每次浏览器只读结果的新 command_id 被误计为新进展 | 停滞检测按原只读能力与业务 result 去重，Fact 检查也复用同一证据身份。修复前，读取相同数据并反复检查的 8 个决策均没有停滞提醒；设置连续停滞上限为 3 的回归在修复后执行 4 个决策并停止（首次检查算有效进展），提前提供提醒。恢复状态、业务变化、新写操作和普通 provider ID 有边界测试。 |
| executeCommand 的异常处理覆盖服务端已确认回执 | 在动作结果已获服务端 ACK 后，后续 getRun/reconcile 断线会把本地 confirmed 改成 unknown。新增完整 executeCommand → ACK → 后续失败 → reload 回归，修复后保留 confirmed，只重试恢复步骤；handler 和结果提交各一次。此前直接 flushReceipts 的回归没有覆盖这层异常处理。 |

对上述 7 个真实模型任务的已保存状态进行离线重建，同一组终态观察从 37 条变为 27 条，观察 JSON 正文从 8,830 字符变为 6,630 字符。正常查询、开始、揭晓分别由 3/5/6 条观察变为 2/3/4 条。这里只测量观察视图，未重新调用模型或执行业务，不能把它当作整个上下文、token 费用或任务请求数的节省。指标见 [evidence/lottery-progress-replay-2026-10-03.json](evidence/lottery-progress-replay-2026-10-03.json)。

这批修复减少重复证据并让已有停止/恢复机制按预期生效，不证明开始任务的模型措辞问题已消除。框架 Go race 测试、vet、命令构建及 Web 69 项测试通过。
