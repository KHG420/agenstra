# 抽奖接入的模型开销定位与优化

日期：2026-10-03。只修改 Agenstra 框架，抽奖软件继续使用原 handler、SDK 构建和业务接口；真实模型验收在独立的虚构活动数据库副本上运行。

## 原四场景的逐轮归因

先只读检查原 `agent/data/runs.sqlite3`、`live-report.json` 和持久化 Facts，而不是根据请求总数推测原因。原始验收记录继续保留在[接入报告](lottery-integration-findings.md)。

每个任务另有 1 次 `memory_extraction`，因此模型请求数不能等同决策数。所有请求的 `attempts` 均为 1，没有网关 HTTP 重试。原始解析失败响应未保存，无法确定具体字段错误，本次没有据此放宽决策校验。

本轮第二组基线另外捕获到 1 个完整的解析失败样本：网关响应 HTTP 200、finish_reason=stop，但 content 是非 JSON 的工具协议片段。框架虽然请求 `response_format: json_object`，仍须拒绝该内容并消耗后续纠正轮次。这个样本不能用来推断未保存的历史失败原因，也不能证明本次框架修改消除了网关输出格式问题。

原揭晓任务累计输入 268,561、输出 30,792 token。最后一轮能力目录为 14,763 字符，Facts 为 14,255 字符，总输入 40,859 字符，低于 80,000 字符预算；没有触发预算压缩。供应商最后一轮报告输入 12,932 token。这是多轮累积和目录重复的成本，不是单轮超出上下文窗口。

## 根因与框架修改

### 1. 异步完成后，模型仍被指向初始排队 Fact

`AgentHost.poll` 用当前轮询结果替换 `RuntimeState.Facts` 中的旧回执；`Invocation.FactID` 也更新为当前结果。原动作的审计 Observation 仍引用旧 ID，而模型观察和 `progress.completed` 原来直接复制这个引用。

例如原揭晓任务的 `47d0d871-edfa-4eaa-8dc1-1b22bdccbb91` 是 `ui.read_activity` 的 queued 回执。它在审计 artifacts 中存在，但不在模型可检查的活动 Facts 中。模型检查它得不到业务结果，随后出现重复检查、重读和错误引用。

现在仅在构建模型观察和进度视图时，将已移出的初始 Fact 引用指向**同一 invocation 的、仍保留的轮询 Fact**。完整审计 Observation、原始 Fact、持久化格式和业务执行结果保持原样。不同 invocation、仍存在的 Fact、错误观察和不可用的轮询证据不会被借用。失败仍显示为 blocked，不确定操作仍为 pending；成功读取状态接口不能把失败操作变为成功。

回归测试在修复前复现了旧引用，在修复后验证当前 Fact 引用和审计状态完全不变，并覆盖多次轮询、操作隔离、失败和不确定结果。

### 2. 每轮重复把宿主轮询配置交给模型

16 个浏览器动作的目录原来各自重复 operation ID/status 路径、轮询参数、pending/success/failure 状态、间隔和超时。这些绑定由框架执行，模型只需要知道页面观察前置和完成结果的来源。

浏览器动作的 `ModelView` 现在保留 `operation.poll_capability = ui.command_status`，并标注 `requires_browser_context = true`。完整 provider 契约、fingerprint、inspect_capability 输出、Schema 校验及执行绑定保持原样；普通 REST/MCP 异步 operation 仍保留原目录信息。抽奖能力目录从 14,763 降到 10,107 字符，减少 4,656 字符（31.5%）。

### 3. 已定位但仍会发生的页面刷新恢复

读取中奖名单的 `operation_failed` 来自持久回执中的 `browser_context_changed`：揭晓改变页面状态后，模型没有先重新 `ui.get_context`，SDK 在 begin 前发布了当前页面观察，服务端版本检查拒绝了旧观察绑定的命令。业务 handler 没有运行；模型刷新后恢复。

这条路径与旧 Fact 引用不同。provider 指令已经要求下一次页面动作前刷新 context，本次目录也明确了这个前置条件；仍有模型漏做的样本。页面版本检查继续生效，不自动重放命令、不隐藏失败，也不把它算作彻底修复。

## 真实模型对照方法

对照基线为本 PR 上一轮的 `b9b2c1c`，其中已有纯浏览器接入、只读重读和引用拒绝反馈。它与原 10 / 6 / 26 / 6 历史验收不是同一次运行，不能把两组数字混用。

前后均从同一份 sample=true 活动准备独立 D1 副本：156 人、revision 6、2 轮历史、无进行中轮次。使用相同网关配置、动作契约、宿主代码、任务指令、30 个模型轮次和 600 秒运行预算，不调大预算。每轮另有独立 Agenstra run/web 数据库。

四个任务保持原指令：只读人数与奖项余量；审批后仅开始；审批后揭晓并读取保存名单；打开记录和切换主题。验收断言保留开始不增加历史、揭晓保存一轮、重复 finish 不改变 revision/中奖 ID，以及 panel/theme 最终状态。开始与揭晓各审批一次。

请求和 token 使用供应商实际报告值；耗时是测试脚本观察到任务终态及诊断的墙钟时间，包含网关、页面协议等待和测试审批，不是纯模型延迟。没有配置模型价格，因此不报告货币成本。框架自动轮询不调用模型。

详细本机证据位于框架工作树的忽略目录 `local/model-overhead-20261003/`；原宿主报告和数据库未改写。临时网关只记录虚构任务的响应，不记录凭据或请求头。所有服务只在 loopback 上启动并在 finally 中关闭。

## 对照结果

两组前后对照共 16 个任务全部 completed，终态错误码为空；开始与揭晓的审批、业务状态、重复 finish 和页面状态断言均通过。每组数字按运行顺序排列，不将历史验收的 26 次当成本轮对照基线。

| --- | --- | --- | --- | --- | --- | --- |
| 只读概览 | 5 / 5 | 4 / 4 | 27,458 / 27,474 | 16,633 / 16,583 | 17.30 / 14.09 | 14.43 / 19.77 |

优化版 8 个任务没有 inspect 初始排队 Fact，也没有最终引用拒绝；基线有 5 次对终态中已移出的 queued Fact 的检查和 1 次最终 Fact 引用拒绝。优化版无 `browser_context_required`，但第一组揭晓仍有 1 次 `browser_context_changed` 后恢复，第二组没有。解析失败从基线 1 次到优化版 0 次仅是这批样本的结果，不能证明外部网关格式问题已修复。

第二组只读任务虽然少一次请求，但耗时反而更长，该次累计输出也从 2,025 增至 3,231 token。请求数、输入量和墙钟时间是不同指标，模型生成长度及网关波动仍会影响耗时。页面导航仍为 6 次请求，输入量约少 20%；它的 5 个决策是两次页面观察、两次页面动作和最终回答，本次没有通过跳过观察或关闭记忆来缩减流程。

逐 Run ID 的脱敏指标、错误计数、检查目标状态和决策序列见 [model-overhead-measurements.json](model-overhead-measurements.json)。完整本机模型回答与数据库保留在忽略目录，不提交凭据或人员资料。

## 验证与限制

普通回归和 CI 不访问模型网关。此次没有修改宿主源码、审批保护、重复写保护、决策/引用校验，也没有新增生产依赖或数据库迁移。模型请求数仍包含当前配置启用的记忆提取；页面导航依然需要观察、页面动作和最终回答，不能将所有这些请求算为无效开销。

相关回归和项目 CI 所需检查已执行：`go test -race ./...`、`go vet ./...`、`go build ./cmd/...`、`npm test --prefix web`（60 项）、`gofmt -l .` 和 `git diff --check`。真实模型四场景使用的临时服务均已停止；未启动浏览器或 Docker 测试资源。

少量虚构活动验收可以证明实际运行结果和本次样本的成本变化，不能证明生产成功率或固定的请求数上限。未保存的历史解析失败仍缺少具体字段证据；页面状态变化、用户编辑和网关输出波动仍可能引发恢复轮次。
