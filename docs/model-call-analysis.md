# 真实模型调用审计与后续优化依据

日期：2026-10-03。此前[模型开销报告](model-overhead-findings.md)记录的是 `b9b2c1c` 与 `dea90c5` 的两组前后对照。本报告继续分析真实 HTTP 请求、响应 usage 和决策序列，并记录独立的模型参数试验；两批数字不混用。

本次参数对照固定 `dea90c5` 框架二进制。该版本的代码已随 PR #29 合并到 main 的 `e1cecb4`。宿主 handler、SDK、业务接口和原数据库不改动，任务只使用独立的 `sample=true` 虚构活动副本。参数由忽略目录内的 loopback 代理注入，**正式部署的模型配置和默认参数没有改变**。本次代码修改仅为失败观察补上实际操作回执的 Fact 引用。

脱敏逐任务指标、决策序列和参数分组见 [model-call-audit.json](model-call-audit.json)。完整本机请求与响应保留在忽略目录 `local/model-overhead-20261003/`，不提交凭据、请求头、数据库或完整人员回答。

## 1. 当前部署把记忆分类也交给默认高强度推理

捕获的普通请求包含 `messages`、`model: deepseek-v4-flash` 和 `response_format: {"type":"json_object"}`，没有 `thinking`、`reasoning_effort` 或 `max_tokens`；响应报告的模型名是 `deepseek-flash`。这些是实际报文中的字段，不据此推断网关内部路由。框架已有全局输出 token 上限支持，当前部署未配置。

[DeepSeek 推理文档](https://api-docs.deepseek.com/guides/thinking_mode)说明：推理默认开启、强度默认 high，可以通过 `thinking: {"type":"disabled"}` 关闭，或通过 `reasoning_effort: "low"` 降低强度。推理模式下 temperature 不生效，因此设置 temperature=0 不能解决本次开销。

上轮优化后八个任务的 47 次实际响应，进一步拆分如下：

| 指标 | 总量 | 其中记忆提取 |
| --- | ---: | ---: |
| 请求 | 47 | 8 |
| 输入 token | 238,868 | 4,226 |
| 缓存命中输入 token | 193,146 | 2,810 |
| 输出 token | 26,048 | 7,030 |
| 推理输出 token | 21,828 | 6,808 |
| 累计模型请求耗时 | 144.564 秒 | 35.912 秒 |

推理占总输出的 83.8%；记忆提取只占输入的 1.8%，却占模型请求耗时的 24.8%。`AgentHost.work → prepareMemories → extractRunMemories` 在首次业务决策之前同步完成记忆提取。此前一个只读任务仅此步骤就耗时 10.955 秒、输出 2,278 tokens，最终只是产生这次任务的临时限制。

抽奖样本的记忆提案为空或 `temporary`；`applyMemoryInput` 明确跳过 temporary，这些运行结束后 memories 和 memory_evidence 都为零。不能由此认为记忆系统无用，但这证明一次性任务的首轮延迟承担了大量没有形成持久记忆的推理。

## 2. 参数对照：辅助提取有明确收益，业务推理须保留验收

每个参数组从相同虚构活动 fixture 的独立副本开始，使用相同四条指令、页面协议、审批步骤和预算。前三组完整执行四场景；全关闭组在揭晓业务断言失败后停止。每组只有一套样本，随机生成、网关延迟和错误恢复会影响数字。

| 参数组 | 只读 / 开始 / 揭晓 / 页面任务请求 | 累计任务墙钟 | 业务验收 |
| --- | --- | ---: | --- |
| 原部署参数 `audit-current` | 4 / 5 / 9 / 6 | 88.910 秒 | 四项通过 |
| 仅记忆关闭推理 `audit-memory-off` | 5 / 5 / 10 / 6 | 77.228 秒 | 四项通过 |
| 记忆关闭、业务 low `audit-low` | 4 / 5 / 7 / 6 | 64.963 秒 | 四项通过 |
| 所有推理关闭 `audit-all-off` | 5 / 4 / 3 / 未执行 | 24.388 秒，部分执行 | **揭晓失败** |

墙钟包含模型调用、页面协议、轮询等待与测试审批；模型请求耗时是代理观察的一次 HTTP 调用总时长，两者不能混作一个指标。每个任务的请求数包含一次记忆提取。

| 参数组 | 记忆输出 token | 记忆推理 token | 记忆调用耗时 | 业务决策调用耗时 |
| --- | ---: | ---: | ---: | ---: |
| 原部署参数 | 4,648 | 4,492 | 22.699 秒 | 44.789 秒 |
| 仅记忆关闭推理 | 24 | 0 | 3.071 秒 | 54.947 秒 |
| 记忆关闭、业务 low | 24 | 0 | 2.805 秒 | 45.039 秒 |

仅记忆关闭推理的四次提取，输出减少 99.5%，耗时减少 86.5%。但该组业务决策从 20 次增至 22 次，并出现页面前置、异步失败与格式恢复；不能把辅助步骤的改善直接当成全任务固定收益。low 组业务决策为 18 次、没有错误样本，但业务决策耗时与默认组相近；不能声称降低 reasoning_effort 必然提高每次决策速度或保证成功率。

关闭全部推理的揭晓任务状态是 `completed`，但模型只读取 context/activity，随后要求用户先文字确认，再执行停止与揭晓。它没有调用 `ui.finish_round`、没有生成正式审批，进行中轮次仍存在，历史没有增加。它没有伪造中奖结果或绕过审批；问题是**回复结束并不代表用户目标已经完成**。三次请求不能记为成功的成本优化，业务状态断言正确地判定了失败。

### 记忆关闭推理的七个分类对照

额外进行了模型提取接口回放，不写入持久化记忆。覆盖一次性读取、一次性开始、中文报告习惯、明确长期中文偏好、项目计量单位约定、忘记已有偏好和这次使用英文。七项均通过预期 mode、key 和原文 quote 校验；临时语言输出 temporary，持久化路径会忽略它。合计输出 215 tokens，无推理输出。

这支持辅助提取使用较小推理预算的方向，但只验证小样本分类，不代表完整的习惯累积、冲突处理和遗忘持久化均经过真实模型验收。不能据此使用关键词规则跳过提取，也不能全局关闭推理。

## 3. 本次落地：让异步失败关联其真实回执

真实揭晓样本中，页面已变化而下一动作使用旧观察，命令在 begin 前被拒绝；回执 `data.error_code` 是 `browser_context_changed`。模型原来只收到 `operation_failed`，失败 Observation 没有关联其回执，progress.blocked 也无法指向具体原因。此时重新读取活动只能间接推测失败原因。

`AgentHost.operation` 的 FailureStates 分支现在把当前 `fact.FactID` 传给 `Reject`。失败仍为失败，不确定结果仍需 reconciliation，参数与错误码保持原语义。修复使用已有字段，不增加恢复提示文本，不改变公共 API、审批、持久化格式或重试策略。

回归先通过真实浏览器夹具复现 observe → dispatch → 页面变化 → begin 拒绝 → poll/Drive，并验证修复前 blocked 没有引用；修复后必须引用仍可用的 `ui.command_status` Fact 及 browser_context_changed 原因。另覆盖普通业务失败和 unknown，保证不会将它们改写为可重试的浏览器错误。

最终代码使用原部署参数另跑四场景 `receipt-current`：请求 4 / 5 / 10 / 6，四项业务断言全部通过。揭晓过程中一次旧页面上下文失败后刷新恢复，另有一次模型格式失败；累计墙钟 91.596 秒。它没有比默认参数对照减少总请求，**本次证明的是失败证据关联被修正，尚未证明这个修复单独降低成本**。

## 4. 缓存与推理 usage 应分开观察

上轮 238,868 个输入 tokens 中，193,146 个命中缓存，占 80.9%。缩短输入仍能降低上下文占用，但输入下降 41.7% 不能直接等同费用下降 41.7%。未配置可核对的供应商价格，本报告不推算货币节省。

当前 `ModelCallMetrics` 已区分 `decision` / `memory_extraction`、总输入/输出与延迟，但未保留 cached input 和 reasoning output 拆分。后续可在框架层增加供应商 usage 的分项观测和有价格依据的估算。缓存 token 仍占上下文，不能因为命中缓存就从 token 预算中扣除；推理输出也不能从真实输出预算中消失。

## 5. 当前中文初始检索不能支撑直接缩小目录

实际首轮目录共 19 项：16 个浏览器动作、保留观察能力及接入占位信息。目录约 10,107 字符，初始系统提示约 7,537 字符；无业务 Facts 的首次决策仍约 4,824 输入 tokens。后续系统提示随能力状态约为 7,693 字符。这些是捕获样本，不是所有任务的固定大小。

`selectedCapabilityNames` 和 `searchAuthorizedCapabilities` 使用 `strings.Fields` 拆词，再做子串评分。按代码对捕获目录回放四条完整中文指令，四项初始匹配都是零。短中文关键词仍可匹配，因此这是完整自然语言指令的初始检索限制。

如果将 limit 直接设为 8，当前字母序兜底为：

```text
lottery.integration_info
ui.cancel_round
ui.command_status
ui.delete_person
ui.delete_prize
ui.export_winners
ui.finish_round
ui.get_context
```

它缺少 read_activity、start_round、open_panel 和 set_theme，可能把常规任务变成额外搜索轮次。本次没有运行启用 limit 的真实模型性能对照，不声称已测得变慢。后续应先改善多语言初始匹配，并在选择动作时保留必要前置能力，再比较总调用成本；本次不增加分词依赖、向量检索或新的抽象层。

## 6. JSON 模式仍出现网关协议片段

即便实际请求使用 json_object，本轮默认组、仅记忆关闭组及最终代码组仍捕获到非规范响应：有的合法 JSON 后附 DSML 关闭标签，有的只输出原生工具协议片段。它们触发严格决策解析失败并增加恢复请求。

[DeepSeek JSON 文档](https://api-docs.deepseek.com/guides/json_mode)要求 json_object、提示中的 JSON 指示及输出例子；框架已有这些指示。不能据此确定是模型、别名路由还是网关转发的问题，未将它计为框架已修复缺陷。没有完整历史响应的早期失败也不能归因到同一原因。

后续应加入部署前的网关结构化输出一致性验收和可区分的格式诊断。保留严格 JSON、引用与审批校验；截取 JSON 前缀、剥除尾部协议片段或自动接受不完整响应，会把外部契约问题掩盖起来。

## 后续优先级与本次范围

1. **框架按调用目的配置模型与推理预算。** 沿用现有 purpose 的划分，将 memory_extraction 与 decision 的参数集中放在框架部署侧；宿主只接入业务能力与选择配置，不承担模型路由。辅助提取是本批最明确的优化对象，业务 low 须扩大成功率与审批验收后再设默认。本次未新增公共配置/API，也未调整生产默认参数。
2. **分项 usage 与部署一致性观测。** 明确缓存输入、推理输出、首次决策前延迟、格式失败及恢复轮次，结合可核对价格衡量费用；对网关 JSON 契约建立实测依据。
3. **多语言能力选择。** 先验证中文指令召回与前置能力覆盖，再缩小首轮目录。避免只减少某轮输入、却增加工具搜索与恢复的总成本。
4. **用业务效果验证省下的调用。** 本次全关闭样本表明，仅检查 completed 和请求数会产生假阳性；开始、揭晓、审批、保存名单与页面最终状态的断言应持续保留。
