## 复现并修复的框架缺陷

**服务端已恢复会话、恢复响应却丢失时，SDK 会另开会话并遗弃原任务。**

触发链为：任务等待审批 → 刷新页面 → 服务端把 generation 从 1 改为 2，并迁移后续绑定 → 响应丢失 → SDK 仍持有 generation 1 → 重试返回 browser_generation_changed → SDK 清除旧连接并创建另一个 session。原任务绑定仍指向原 session，新的“已连接”状态不能执行原任务。

真实模型案例保存了修复前的两个不同 session ID，业务写入尚未执行。稳定 SDK 回归在修复前因“另建了一个会话”失败。完整修复所需的可选协议字段和持久身份已获得本轮明确授权。

修复沿用现有会话和存储路径：

- resume 请求支持可选 `request_id`；SDK 发送前保存身份，网络/网关失败后保留，重新加载后继续使用同一个身份。
- 服务端在原 SQLite 事务和会话 JSON 中保存最后一次恢复 ID。只有同一 owner、有效 key、原 generation 和最后一次 ID 匹配的重试可以取得已恢复的当前会话。
- 重试不再次递增 generation、不重置已发布的页面观察，也不把新代数已运行的命令改成 unknown。
- 后续另一恢复会使旧请求失效；关闭、profile 漂移和错误身份仍被拒绝。第一次恢复对旧运行中命令的 unknown 语义及禁止自动重放规则保持有效。
- SDK 先保存返回的新 generation，再清除恢复身份。原 Go 方法和不传 request_id 的旧客户端继续使用既有协议，没有新增数据库表或生产依赖。

真实模型修复后测试覆盖响应丢失后的原客户端重试，以及再次加载客户端后的持久重试。两者均保留原 session、仅增加一次 generation、完成审批和修改，实际读回符合目标。

## 保留的失败和实验限制

发现阶段五组场景有三组通过：普通审批刷新的一次模型请求超时，业务修改和读回已成功但任务最终 failed；恢复响应丢失的一组暴露上述框架缺陷。没有把前者算为业务和任务同时成功。

扩展阶段十八组场景有十七组断言通过。队列取消的一组由于测试脚本沿用“应修改至 90”的检查，在实际保持 12 时错误失败，已修正。该队列中的下一条读取已由服务端完成，虽不在当时已写出的 step 列表中，也补入最终账本；不补造该条的自动质量断言。失败收尾现在取消同一实验会话尚未终止的其他消息。两条已发布取消任务的初始用量采集也有缺失，最终统一从服务端诊断补齐，而非保留零请求误计。

修复后的针对性四组场景及确认阶段十一组场景全部通过。正式界面三条消息中，两条 completed，一条因审批等待超过配置的 180 秒期限而 failed/run_deadline_exceeded；业务未修改，后续回答明确说明这一点。运行时间预算包括审批等待，接入方需要按人工工作流设置预算。本轮未放宽该策略，也没有把超期失败抹掉。

宿主已接入八个业务能力，本轮实际调用 `ui.list_users`、`ui.get_user`、`ui.update_user` 和 `ui.list_groups` 四个能力，账本共有 166 条业务命令，其中 30 次用户修改成功；其余四个能力没有在本轮再次调用，此前接入验收见 [接入报告](sub2api-integration-findings.md)。没有使用生产用户、真实上游账号、支付业务或生产负载；三路提交测试不等同于容量基准。部分查询存在冗余读取，模型格式恢复及网络超时均保留证据，不能从单次恢复请求数推导普遍性能提升。
